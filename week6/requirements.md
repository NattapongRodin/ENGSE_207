# Requirements Analysis — Online Meeting Room Booking System

## Functional Requirements
1. ผู้ใช้ต้องสามารถดูรายการห้องประชุมทั้งหมด พร้อมความจุ/อุปกรณ์/สถานะการใช้งานได้
2. ผู้ใช้ต้องสามารถดูปฏิทินการจองของแต่ละห้อง (รายวัน/รายสัปดาห์/รายเดือน) และค้นหาช่วงเวลาว่างได้
3. ผู้ใช้ต้องสามารถสร้างการจองห้องประชุมแบบครั้งเดียว (One-time booking) โดยระบุห้อง/วันเวลา/หัวข้อ/ผู้เข้าร่วมได้
4. ผู้ใช้ต้องสามารถสร้างการจองแบบทำซ้ำ (Recurring) เช่น ทุกวันจันทร์ 10:00–11:00 เป็นเวลา 8 สัปดาห์ได้
5. ระบบต้องป้องกันการจองชนกัน (Double booking) และแจ้งเหตุผลเมื่อจองไม่สำเร็จ
6. ผู้ใช้ต้องสามารถแก้ไข/ยกเลิกการจองของตนเองได้ (ภายใต้นโยบาย เช่น ห้ามยกเลิกก่อนเริ่ม < 30 นาที)
7. ระบบต้องส่งการแจ้งเตือน (Email/LINE) เมื่อมีการสร้าง/แก้ไข/ยกเลิกการจอง และก่อนเริ่มประชุม (เช่น 15 นาที)
8. ผู้ดูแลระบบ (Admin) ต้องสามารถเพิ่ม/แก้ไข/ปิดปรับปรุงห้อง (Maintenance) และกำหนดเวลาที่ห้องไม่พร้อมใช้งานได้

## Non-Functional Requirements
1. **Performance:** หน้าดูตารางการจองของห้องต้องโหลดเสร็จภายใน 2 วินาทีสำหรับข้อมูล 1 เดือน (ผู้ใช้พร้อมกันระดับห้องเรียน/ภาควิชา)
2. **Availability:** ระบบพร้อมใช้งานอย่างน้อย 99.5% ต่อเดือน (ยกเว้นช่วงบำรุงรักษาที่ประกาศล่วงหน้า)
3. **Security:** ต้องมีการยืนยันตัวตน (Authentication) และกำหนดสิทธิ์ (Authorization) อย่างน้อย 2 บทบาท: User/Admin
4. **Reliability:** การจองต้องเป็นแบบ atomic/consistent (สร้างไม่สำเร็จต้องไม่เกิดข้อมูลค้าง) และป้องกันการจองชนกันได้จริง
5. **Maintainability:** โค้ดต้องแยกโมดูลชัดเจน สามารถเพิ่มช่องทางแจ้งเตือนใหม่ (เช่น Slack) ได้โดยกระทบส่วนอื่นน้อย
6. **Auditability:** ต้องเก็บประวัติการเปลี่ยนแปลงการจอง (ใคร ทำอะไร เมื่อไหร่) เพื่อการตรวจสอบย้อนหลัง

## Constraints
1. **Team/Time:** งานเดี่ยว ระยะเวลาพัฒนาและทำเอกสารจำกัด (เช่น 1–2 สัปดาห์สำหรับต้นแบบ)
2. **Technology:** ต้องใช้เทคโนโลยีที่เรียน/คุ้นเคย (ตัวอย่าง: React + Node.js/Express + MySQL) และทำงานได้บนเครื่องนักศึกษา
3. **Cost/Infra:** ใช้บริการฟรีหรือค่าใช้จ่ายต่ำ (เช่น Deploy แบบง่าย: VPS ราคาถูก หรือ PaaS ฟรี) ไม่พึ่งระบบราคาแพง
4. **Integration:** การแจ้งเตือน LINE ต้องใช้ LINE Messaging API (หรือ LINE Notify หากอนุญาต) และ Email ผ่าน SMTP/Service ที่ใช้งานได้จริง
5. **Data:** ต้องปฏิบัติตามหลักการเก็บข้อมูลส่วนบุคคลขั้นต่ำ (เก็บเฉพาะข้อมูลจำเป็น เช่น email/lineId)

## Quality Attribute Scenarios

### Scenario 1: Prevent Double Booking Under Concurrent Requests
- **Quality Attribute:** Reliability / Consistency
- **Source:** ผู้ใช้ 2 คน (หรือ 2 แท็บ) จองห้องเดียวกันช่วงเวลาเดียวกัน
- **Stimulus:** ส่งคำขอ Create booking พร้อมกัน (within < 1 second)
- **Artifact:** Booking Service / Database
- **Environment:** ระบบทำงานปกติ มีผู้ใช้พร้อมกันระดับ 50–100 คน
- **Response:** ระบบยอมรับได้เพียง 1 รายการ อีกคำขอถูกปฏิเสธพร้อมข้อความ “time slot unavailable”
- **Response Measure:** อัตรา double booking = 0, เวลาตอบกลับการจอง < 1.5 วินาที

### Scenario 2: Notification Delivery Before Meeting
- **Quality Attribute:** Availability / Reliability
- **Source:** ระบบ Scheduler/Job runner
- **Stimulus:** ถึงเวลา T-15 นาทีของการจอง
- **Artifact:** Notification Module + Email/LINE Provider
- **Environment:** ระบบทำงานปกติ แต่ผู้ให้บริการส่งข้อความอาจหน่วง/ล่มชั่วคราว
- **Response:** ระบบส่งแจ้งเตือน และหากส่งไม่สำเร็จให้ retry ตามนโยบาย (เช่น 3 ครั้ง ภายใน 10 นาที) พร้อมบันทึกสถานะ
- **Response Measure:** อัตราส่งสำเร็จ ≥ 98% ภายใน 5 นาที, มี log ตรวจสอบได้ทุกครั้ง
